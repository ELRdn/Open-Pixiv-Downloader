# タグ一括保存の不具合調査

調査：2026年11月10〜11日。対象alpha.8、修正版alpha.9。

## 実行ログと実APIで確認した原因

| 症状 | 原因・確認結果 |
|---|---|
| 約16.4万件の小説タグが1要求で失敗 | ツール独自の `total > 100000` 判定。API自体は正常応答していた。実測総数163,727件 |
| 524件のタグが300件・10要求で失敗 | 今回の匿名APIは `lastPage=10` を返す。11ページ目を要求しても10ページ目と同じ結果で、単純なページ番号の増加では続きへ進まない |
| 日付分割しても524件に対して516件しか集まらない | 開始日を指定した長期間検索が実際には約1年に切り詰められた。`scd=2025-01-01` の検索は2025年11月以降の148件だった。一方、期間を明示すると2024年以前223件、2025年171件、2026年130件となり合計524件で一致 |
| 未取得のままF11を案内しても再開できない | 列挙の途中状態が保存されず、未確定一覧の再開は拒否されていた |
| 停止理由に「ワーカー異常」、詳細がログから流れる | 検索一覧の失敗も一般のワーカーエラーとして分類し、その後の集計ログで原因が見えなくなっていた |

10万件という数値はサービス側の上限ではない。ページ窓・期間検索の挙動は、今回の匿名接続と検索条件で確認した実装依存のもので、公式APIの保証とは扱わない。

## 修正

- 検索・統合・保存一覧の再開で作品数上限を100万件に統一。再開用JSONは64MiBまで。
- 取得したユニークID数と応答の総数を照合し、打ち切られた区間を日付で分割。隣接する区間は「境界日以前」と「翌日以降」で、日付を落とさない。
- 開始日付きの検索は終了日を明示し、365日以内の区間に分ける。期間の終端は同条件の最新投稿から確認し、根拠のない開始年は仮定しない。
- 分割前に観測したIDの欠落や件数減少も検出し、不完全な一覧を完了として公開しない。
- 既存SQLiteに一覧ページのID・投稿日時等を増分保存。本文・画像は列挙段階では取得しない。全一覧を毎ページJSONへ書き直す方式は使わない。
- 列挙途中の再開を追加。検索条件・選択上限と処理の世代を保存し、古い別ジョブのキャッシュと混在させない。
- 確定済み一覧の再開で処理件数を減らしても、保留されたIDを元の保存一覧から落とさない。
- 検索失敗は「検索一覧の列挙が未完了」と表示し、失敗時に詳細を開く。再開可能な中断と、元URLからの再確認が必要な状態を区別する。

## 検証の範囲

10ページ上限とページ反復を再現する合成APIで、524・163,727・164,000件の全ID、重複、日付境界、閏日、昇順・降順、期間の切り詰めを検証済み。検索中断・再開、一覧の保存・読み戻しも別に検証した。大量の本文ファイルを生成するテストではない。

Windowsのalpha.9候補で、報告された524件のタグを実APIで全列挙した。最初のプロセスを要求予算12回で停止し、保存済み12ページを再利用した別プロセスで27回追加要求して完了。選択524件・ユニーク524件で一致した。検索条件やタグ名を公開する必要がないため、ここでは件数のみ記録する。

ローカルのRustテスト121件、`cargo fmt --check`、全ターゲットのClippyが成功した。確定一覧を小さい上限で繰り返し再開しても、旧形式を含め元の全IDが保持されることも検証した。

実サイトの確認は一覧メタデータに限定する。約16.4万作品の本文・画像を全取得したという検証ではない。

## 残る制約

- 一日だけに絞っても到達可能なページ数を超える場合は、その日付と件数を示して停止する。未取得分を飛ばしたり全件完了と表示したりしない。
- 長時間の検索中に新規投稿・削除・タグ変更があると結果は変動する。検索APIには厳密な時点スナップショットの保証がない。
- 要求予算は作品数と別。164,000作品なら本文の取得だけでも164,000要求以上になるため、alpha.9の最大予算100,000を超える。alpha.10以降は上限を1,000,000へ拡大し、F10または `--request-budget` で変更できる。予算到達時は一時停止し、F11で続行する。
- 拒否応答や通信・ディスク障害での停止、原本保護と保存後の整合性検証は維持する。
