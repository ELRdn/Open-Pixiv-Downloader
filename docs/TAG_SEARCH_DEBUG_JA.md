# タグ一括保存の不具合調査

## 2026年11月14日追補（alpha.19：密集日の全件処理）

「オリジナル」2026-11-13の一日分を、実サイトで全935ID列挙し、全件を処理した。以前の939件から総数が変わっており、今回の開始時の総数935件とユニークID数が一致する。本文872件（既存152件＋新規720件）・方針による除外62件・HTTP 404で取得不可1件で935件すべてを照合した。本文872件・11,639,155バイトはサイズとSHA-256を検証。同じ一覧の再開は追加要求0回だった。404の作品を取得済みとは扱わない。Pixiv全期間の「オリジナル」本文を全取得した検証ではない。

日付・新旧両方向のページ送りだけでは、密集日に到達できない中間のIDがある。[公式の検索基盤の記事](https://inside.pixiv.blog/2024/08/26/160000)が説明するAND・OR・NOT・括弧の検索構文を使い、元の語句を `( 元の条件 )` として保持し、「語を含む／含まない」の互いに反対の条件へ再分割した。空白を含む括弧が必要で、`(オリジナル)` では今回のAPIは一致しなかった。子条件の総数の和、全子条件のユニークID数、親で観測したIDの包含を照合し、不一致は未完了とする。統合後は投稿日時・IDで元の新旧順へ戻す。検索結果由来の候補語は演算子や構文を混入できない文字に限定する。

さらに、APIが総数に数える一方で一覧のIDを省略する公開作品が2件あった。本文APIでは取得でき、ユーザーの除外条件に該当する329バイトと163バイトの作品だった。小説の単一タグ完全一致では、ページ内の省略位置を検出し、隣接する表示IDの周辺を作品情報で確認する。日付はJSTへそろえ、元のタグ・追加の肯定／否定条件・全年齢条件を照合した作品だけを補完する。「オリジナル」が作品のオリジナル属性も対象にする挙動を考慮した。候補範囲を作品全体の網羅と仮定せず、補完後も元の総数と観測IDを満たさなければ停止する。

一覧ページのタグと補完用の最小メタデータを再開キャッシュに保存する。補完照会で取得した本文・プロフィール・画像はキャッシュに残さない。旧版のタグを含まないページは必要時に一度だけ更新し、HTTP 404等の不在IDも今回の列挙世代内で再利用する。予算切れ・取消・HTTP拒否による中断は従来の制御を通る。既存の除外・1,024バイト未満の本文除外も維持する。

制約：検索条件に分割可能な候補語がない場合や、補完用IDが推定範囲の外にある場合は停止する。ID補完は現在、単一語のタグ完全一致と基本フィルターに限定し、未知のフィルターを広げて処理しない。タイトル・キャプション検索等の密集日にも語による分割は適用するが、この補完が必要な不整合が残る場合は未完了とする。検索APIには時点スナップショットの保証がなく、取得中の公開範囲・タグ・件数の変更も未完了として検出する。

## 2026年11月14日追補（alpha.17）

「オリジナル」の小説検索は実APIでHTTP 200、総数1,512,674件だった。alpha.16はツール独自の100万件判定で最初の応答直後に停止していた。作品一覧・統合・再開の上限を1,000万件、再開ファイルの上限を512MiBへそろえて拡張した。本文と検索結果を保持するためメモリー・ディスクの消費量は作品数に応じて増える。要求予算の最大100万回とは別の制限である。

`/search?q=R18&s_mode=tag_tc&type=novel` を受け付け、小説の検索モードを公式フロントエンドの変換に合わせた。`tag_tc` は `s_tag`、`tag` は `s_tag_only`、`tag_full` は `s_tag_full`、`text` は `s_tc`。`s_tc` をタグ・タイトル・キャプション検索として使うと本文検索へ変わってしまうため区別する。元のURLを保存・再開情報に残し、検索語の記号や複数語、対応するフィルターを保持する。現在の `/search` 対応は `type=novel` に限定する。

ただし「オリジナル」は2026-11-13の一日だけで939件あり、匿名APIは30件×10ページの窓しか返さない。新旧両方向で最大600件となり、実際の20要求では599ユニークIDで停止した。既存の日単位分割でもこの日は全列挙できない。時刻付き日付・文字数・ページサイズの指定は今回の匿名接続では無視され、AI除外だけでも729件が残った。これらの指定で全件を列挙できるとは扱わない。全件取得可能になったという修正ではなく、最初のツール側上限を解消し、密集日の不足は日付・観測件数・総数を示して停止する。

WindowsのRustテスト154件、fmt、全ターゲットのClippyが成功。151万2,674IDの合成列挙、同件数・64MiB超の一覧再開、元URLから本文専用保存・重複スキップ・再開、Ctrl+S確認画面を検証した。実APIでは元の2つのURLから2要求ずつ列挙し、以前の入力エラー・100万件エラーを通過して予算停止することを確認。日付を2026-11-13へ絞った `/search` は1要求で29IDを全列挙した。実サイトの検証は一覧だけで、本文の大量取得は開始していない。通常の `opixiv` へalpha.17を導入し、releaseビルドとのSHA-256一致を確認した。開いたままの旧TUIには再起動が必要。

調査：2026年11月10〜11日。対象alpha.8、修正版alpha.9。

## 実行ログと実APIで確認した原因

| 症状 | 原因・確認結果 |
|---|---|
| 約16.4万件の小説タグが1要求で失敗 | ツール独自の `total > 100000` 判定。API自体は正常応答していた。実測総数163,727件 |
| 524件のタグが300件・10要求で失敗 | 今回の匿名APIは `lastPage=10` を返す。11ページ目を要求しても10ページ目と同じ結果で、単純なページ番号の増加では続きへ進まない |
| 日付分割しても524件に対して516件しか集まらない | 開始日を指定した長期間検索が実際には約1年に切り詰められた。`scd=2025-01-01` の検索は2025年11月以降の148件だった。一方、期間を明示すると2024年以前223件、2025年171件、2026年130件となり合計524件で一致 |
| 未取得のままF11を案内しても再開できない | 列挙の途中状態が保存されず、未確定一覧の再開は拒否されていた |
| 停止理由に「ワーカー異常」、詳細がログから流れる | 検索一覧の失敗も一般のワーカーエラーとして分類し、その後の集計ログで原因が見えなくなっていた |

10万件という数値はサービス側の上限ではない。ページ窓・期間検索の挙動は、今回の匿名接続と検索条件で確認した実装依存のもので、公式APIの保証とは扱わない。

## 修正

- 検索・統合・保存一覧の再開で作品数上限を100万件に統一。再開用JSONは64MiBまで。
- 取得したユニークID数と応答の総数を照合し、打ち切られた区間を日付で分割。隣接する区間は「境界日以前」と「翌日以降」で、日付を落とさない。
- 開始日付きの検索は終了日を明示し、365日以内の区間に分ける。期間の終端は同条件の最新投稿から確認し、根拠のない開始年は仮定しない。
- 分割前に観測したIDの欠落や件数減少も検出し、不完全な一覧を完了として公開しない。
- 既存SQLiteに一覧ページのID・投稿日時等を増分保存。本文・画像は列挙段階では取得しない。全一覧を毎ページJSONへ書き直す方式は使わない。
- 列挙途中の再開を追加。検索条件・選択上限と処理の世代を保存し、古い別ジョブのキャッシュと混在させない。
- 確定済み一覧の再開で処理件数を減らしても、保留されたIDを元の保存一覧から落とさない。
- 検索失敗は「検索一覧の列挙が未完了」と表示し、失敗時に詳細を開く。再開可能な中断と、元URLからの再確認が必要な状態を区別する。

## 検証の範囲

10ページ上限とページ反復を再現する合成APIで、524・163,727・164,000件の全ID、重複、日付境界、閏日、昇順・降順、期間の切り詰めを検証済み。検索中断・再開、一覧の保存・読み戻しも別に検証した。大量の本文ファイルを生成するテストではない。

Windowsのalpha.9候補で、報告された524件のタグを実APIで全列挙した。最初のプロセスを要求予算12回で停止し、保存済み12ページを再利用した別プロセスで27回追加要求して完了。選択524件・ユニーク524件で一致した。検索条件やタグ名を公開する必要がないため、ここでは件数のみ記録する。

ローカルのRustテスト121件、`cargo fmt --check`、全ターゲットのClippyが成功した。確定一覧を小さい上限で繰り返し再開しても、旧形式を含め元の全IDが保持されることも検証した。

実サイトの確認は一覧メタデータに限定する。約16.4万作品の本文・画像を全取得したという検証ではない。

## 残る制約

- 一日だけに絞っても到達可能なページ数を超える場合は、その日付と件数を示して停止する。未取得分を飛ばしたり全件完了と表示したりしない。
- 長時間の検索中に新規投稿・削除・タグ変更があると結果は変動する。検索APIには厳密な時点スナップショットの保証がない。
- 要求予算は作品数と別。164,000作品なら本文の取得だけでも164,000要求以上になるため、alpha.9の最大予算100,000を超える。alpha.10以降は上限を1,000,000へ拡大し、F10または `--request-budget` で変更できる。予算到達時は一時停止し、F11で続行する。
- 拒否応答や通信・ディスク障害での停止、原本保護と保存後の整合性検証は維持する。
