# pixiv作品アーカイブツール：公開情報と公開ソースによる技術調査

調査日：2026年10月29日（日本時間）
対象：pix-web-DLと既存OSSの取得・保存方式、および独立実装の設計
本資料の位置付け：実装仕様を組み立てるための調査記録。サービス内部の完全な復元や、本番動作の保証を意味しない。

## 1. 結論

イラスト・漫画・うごイラ・小説を共通の管理方式で保存するローカルツールは、公開ソースから読み取れる取得手順を基に設計できる。開発の中心は、個別のダウンロード処理だけでなく、「どの作品を、どの版まで、どの程度完全に保存したか」を記録するエンジンに置くべきである。

pix-web-DLの価値は、作者IDを入力するだけでサーバーが処理し、スマホでZIPを受け取れる簡単さにある。一方、新しいOSSが同じ集中型サービスを最初から運営すると、認証・転送量・一時保存・アカウント制限・ジョブ管理まで引き受けることになる。このため、本提案は「ローカルエンジン → ブラウザ拡張 → 必要ならデスクトップUI」の順とする。

本プロジェクトのPython alphaについて、オンラインのpixiv作品取得は本調査で実測していない。オフラインの合成入力やテストで確認できることと、実サイト上の互換性は別の検証対象である。API仕様、必要な認証、公開範囲、レート制限は環境や時点によって変わり得る。

## 2. 「全て」の範囲を先に定義する

| 意味 | 実際の要件 | 本提案での扱い |
|---|---|---|
| 全形式 | イラスト・漫画・うごイラ・小説を扱う | 目標に含める |
| ある作者の全件 | その時点で取得主体に閲覧権限があり、列挙できる投稿を取得する | 作者単位ジョブとして扱う |
| 全ページ | 漫画等の複数ページを欠落なく保存する | 作品完了の必須条件 |
| 完全な小説 | 本文・記法・表紙・許可された挿絵・シリーズ順序を保存する | 素材ごとの取得状態を明示する |
| 自分のブックマーク全件 | 本人の一覧取得、公開・非公開の区別、認証が必要 | 後続の独立機能 |
| pixiv全サイト | 全作品の発見、権限差、更新・削除、サービスへの負荷まで扱う | 本提案の対象外。作者全件とは別の問題 |
| 削除済み・閲覧不能作品 | 現在返されないデータを復元する | 保証できない |

「全件保存できた」は、列挙結果と保存結果が一致した時点・対象・権限の範囲でのみ成立する。列挙APIが返した集合を、pixiv全体の完全な集合と同一視しない。

## 3. 証拠の強さを区別する

| 区分 | 意味 | 本調査の例 |
|---|---|---|
| 公開ソース確認 | 特定commitのコードや型定義に記載を確認した | 作者一覧API、シリーズのページング、LICENSE |
| 運営者の説明 | サービス運営者の公開ページが説明している | pix-web-DLのZIP上限、料金、サービス側認証 |
| 推定 | 観測できる仕様を成立させるために必要と考えられる構造 | バックグラウンドジョブと保存状態の永続化 |
| 提案 | 本プロジェクトが採用するとよい独自設計 | SQLite台帳、ハッシュ検査、版保持 |
| 未確認 | コードの記載や説明があっても実行で確かめていない | 現在の認証なし取得範囲、全形式の実サイト動作 |

公開コードの存在は、そのコードが現在も全てのアカウント・作品に対して動く証拠にはならない。また、運営記事はサービス側の説明であり、第三者による実測結果ではない。

## 4. pix-web-DLについて判明したこと

### 4.1 名称とサービス範囲

2026年8月10日の運営記事は、pixdl.bottomfeeder.netのサービスを「Pixiv Downloader」と呼んでいる。したがって、依頼文の「pix-web-DL」「Pixiv Downloader」を別々の製品と断定できない。Chrome拡張の「Powerful Pixiv Downloader」は比較対象として区別する。[S2]

pix-web-DLは、作者の数字IDを指定し、その作者の公開作品をZIPで受け取るサービスである。利用者のブックマーク一覧、フォロー中の作者全員、検索結果、単独作品の指定は、確認した運営記事では対象外とされる。[S3]

### 4.2 作品と出力

| 作品 | 運営者が説明する出力 |
|---|---|
| イラスト | 原寸画像 |
| 漫画 | 複数ページの画像 |
| うごイラ | GIF |
| 小説 | 元のpixiv記法を残すTXT、読みやすく変換したHTML、表紙・挿絵・メタデータ |

小説対応の告知では、シリーズ名はメタデータとHTMLに記録するが、シリーズ単位のフォルダにはしないと説明されている。小説のみを選ぶ機能も当該記事時点ではない。[S1][S4]

ここから得られる独自実装の差別化案は、「小説だけを選択」「シリーズ順に読める」「原データと変換版の両方を残す」「取得できなかった挿絵を明示する」である。これは既存サービスの内部実装の主張ではなく、出力仕様を比較した設計提案である。

### 4.3 認証の重要な違い

運営者は、利用者のpixivパスワード・Cookie・トークンを受け取らず、サービス側の認証でpixivから取得すると説明している。サービス登録の認証は、メールとサービス用パスワード、またはGoogleログインである。[S3]

つまり「ユーザーがpixivにログインしなくてよい」は「pixiv認証が不要」と同じ意味ではない。ローカルOSSが同じ取得可能範囲を再現できるかは、実際に使う認証主体と作品の公開設定に依存する。

本提案では、ユーザーの認証情報を中央サーバーへ集める構成を初期要件にしない。ブラウザ拡張を追加する段階では、利用者自身が通常のログイン操作を行い、その閲覧権限の範囲でローカル処理へつなぐ設計を検討する。認証情報は作品メタデータ・エラーログ・共有ZIPに含めない。

### 4.4 2026年9月の変更

| 公開日 | 運営者が説明する変更 | 設計に取り入れる点 |
|---|---|---|
| 9月7日 | 残高内の部分DL。差分DLは未取得分と新作を対象にする | 時刻だけでなく、取得済み作品IDの集合が必要 |
| 9月27日 | 10GB到達で完了した作品までをZIP化。残りは差分DLへ送る | 一部完了と全件完了を区別する |
| 9月27日 | 作者ごとの複数ZIP履歴から選択できる | ジョブと作者を1対1にしない |

9月7日の説明では、差分DLは削除検出を目的とせず、自動監視もまだ提供していない。9月27日の説明では、容量境界をまたぐ作品と取得途中の作品を完成ZIPに入れない。[S5][S6]

この挙動を再現するには、少なくとも作者・作品・ジョブ・生成ZIP・保存済み対応関係を永続化する必要がある。ただし、その実現にどのDBやキュー製品を使用しているかは未確認である。

### 4.5 料金・期限の情報は新しいものを優先する

確認した料金ページでは、画像1ページと小説1作を各1単位、うごイラ1作を10単位として計算する。99単位以下は無料、100単位ごとに100クレジット、1依頼の上限は3,000クレジットである。依頼時の見積もりを基準に消費し、実取得との差額返還は行わない。10GBの続きは別依頼となる。[S7]

現在の運営記事が示すZIP受取期限は7日である。8月10日の古い通知記事には30日とあり、現行仕様として引用しない。[S2][S4]

### 4.6 分からないこと

pix-web-DLのサーバーソース、内部API、キュー、DB、フレームワーク、ストレージ、pixiv APIの選択、並列数、待機秒数は確認できていない。公開ホームページの取得が不安定で、今回の環境では公開JS資産も確認できなかった。

サーバーで処理が続くことからバックグラウンド実行は推定できても、Redis、Celery、FastAPI、React、S3などを採用技術として断定する根拠はない。運営者がライブラリを公開しているとする証拠も、本調査では得られていない。

### 5.1 方式を比較する

| 方式 | 得られる利点 | 実装上の負担 |
|---|---|---|
| Web側API | ブラウザ表示に近いデータと小説記法を扱いやすい | 非公式APIの変更、認証状態、フィールド差を吸収する |
| App API | 既存クライアント実装を参照でき、ページング構造がある | トークン管理とApp API特有の仕様を扱う |
| ページHTML解析 | 埋め込みデータがある場合の補助手段になる | HTML変更、ログイン画面、エラーページ誤認が起こり得る |
| 画像URLの推測 | リクエスト数を減らせる場合がある | 拡張子・ページ構成の例外を黙って落とす危険がある |

公開ソースでは、gallery-dlのApp API側に単ページ原寸URLと複数ページ原寸URLを分けて扱う処理があり、Web側にはページ番号を組み立てる処理もある。[R2] 独自実装では、サーバーから明示的に返されたページ一覧・URLを優先し、推測に依存した成功判定を避ける。

## 6. 公開ソースで確認できたAPIの対応

以下は互換実装を調査するための対応表である。pixivが安定した外部向けAPIとして保証した一覧ではない。オンラインでの成功、認証不要、全件取得、長期互換性の保証も含まない。

### 6.1 Web側

| 目的 | パス・パラメータ | 根拠・注意 |
|---|---|---|
| 作者の作品ID列挙 | GET /ajax/user/{user_id}/profile/all | PPD API.ts。illusts・manga・novelsを扱う。[R1a] |
| イラスト等の詳細 | GET /ajax/illust/{work_id} | PPD API.ts。[R1a] |
| 漫画等のページ一覧 | GET /ajax/illust/{work_id}/pages | 別OSS novel.shで使用。本文指定のページは1始まり、配列は0始まり。[R5] |
| うごイラ情報 | GET /ajax/illust/{work_id}/ugoira_meta | PPD API.ts。[R1a] |
| 小説詳細・本文 | GET /ajax/novel/{work_id} | PPD API.ts。[R1a] |
| 小説シリーズ情報 | GET /ajax/novel/series/{series_id} | PPD API.ts。[R1a] |
| シリーズ内の作品一覧 | GET /ajax/novel/series_content/{series_id}?limit=30&last_order=0&order_by=asc | PPD API.tsにページング処理用の引数。[R1a] |
| 小説の参照イラスト | GET /ajax/novel/{novel_id}/insert_illusts?id[]=作品ID-ページ | PPD API.ts。小説内の挿絵として返る結果を確認する。[R1a] |

小説関連の型定義には、seriesNavData、シリーズ内の順序、textEmbeddedImages、参照イラストの結果が定義されている。挿絵の結果が空になる場合を前提に設計する。[R1b]

単体の一般的な作品ページURLは、画像作品なら https://www.pixiv.net/artworks/{id} 、小説なら https://www.pixiv.net/novel/show.php?id={id} である。入力URLの解析は明示的に許可するホストとパスに限定し、任意URLをそのまま取得するHTTPプロキシにしない。

### 6.2 App APIとの対応

pixivpyとgallery-dlには、イラスト詳細・作者作品一覧・うごイラ情報・小説詳細・小説本文・小説シリーズを取得する処理がある。[R2][R4a] ただし、同じ作品でもWeb側とApp側のフィールド名・欠損・認証条件を同じと仮定しない。

古い実装例の`/v1/novel/text`を、そのまま新規実装へ採用しない。調査したpixivpyの`novel_text()`には旧経路が廃止された旨の注記があり、`/webview/v2/novel`を使う関数へ委譲している。[R4a] 関数名が同じでも通信先が変わっている例であり、検索結果の古いサンプルだけに依存しない理由になる。

独自エンジンの内部形式は、Web/APIの応答から切り離す。たとえば「作品ID」「形式」「ページ」「本文」「シリーズ順序」という正規化済みモデルを定義し、取得方式を交換しても保存・変換・整合性確認を共用できるようにする。

### 6.3 列挙と取得を分離する

作者全件の処理は、最初に候補IDを保存し、次に個別作品を取得する。途中で列挙が失敗したときは「作品0件」と「列挙失敗」を別結果にする。空配列だけでは、この違いが分からない。

シリーズでは、APIが返す作品順序を採用する。作品ID順、投稿日時順、ファイル名順は、作者が意図したシリーズ順と一致するとは限らない。ページングの繰り返しで同じIDが返った場合は重複を排除し、同じカーソルが続く場合は無限ループを止める。

## 7. 形式ごとの保存契約

ここからは独自実装の設計提案であり、pix-web-DLが内部で同じ構造を持つという主張ではない。

### 7.1 イラストと漫画

作品と画像ファイルは1対多として扱う。漫画だけでなく複数枚イラストもあるため、「イラストなら画像1枚」と決めつけない。

各画像にはページ番号、取得URL、MIME、サイズ、ハッシュ、取得時刻を記録する。ファイルは一時パスへ書き、成功後に確定パスへ移す。ページが1枚だけ保存できても、残りが失敗した作品をcompleteにしない。

画像は可能な限り元のバイト列を保存する。閲覧用の縮小版・WebP・サムネイルは派生ファイルとして区別する。原寸画像をJPEGへ一律変換してから「原本」と呼ばない。

### 7.2 うごイラ

保存の基準を「素材ZIPとフレーム順・表示時間の情報」とし、GIF等は閲覧用派生物とする。GIFだけでは、保存元と同じ情報を維持したかを確認しにくい。

必要な確認は、ZIPが正常に読めること、参照されたフレームが揃うこと、各delayが有効な値であること、メタデータの順に再生することである。ZIPの名前順をそのままフレーム順と仮定しない。

展開する場合は、ZIP内部の絶対パスや親ディレクトリ参照を拒否し、展開後容量にも上限を設ける。取得したZIPがあるだけで、変換まで成功したと表示しない。

### 7.3 小説

本文は少なくとも次の3表現を分ける。

| ファイル | 目的 | 注意 |
|---|---|---|
| source.txt | 元のpixiv記法を含む本文 | 変換のために上書きしない |
| plain.txt | 読み上げ・全文検索などの平文 | ルビやリンクの処理方針を記録する |
| index.html | 読むための表示 | HTMLエスケープと安全なリンク処理が必要 |

pixiv公式ヘルプは、章・改ページ・挿絵・ページ内リンク・外部リンク・ルビ・太字・斜体・傍点の記法を説明している。参照挿絵には作品作者の承認が必要な場合もある。[S8] したがって、一般的な小説本文でもルビ・改ページだけを置換する実装では不十分である。

パーサーは、記法をトークンに分け、構造を保持してから各形式へ変換する方式を推奨する。複数の正規表現を順に適用するだけでは、生成したHTMLに次の置換が作用したり、未対応記法を落としたりする危険がある。

未対応または壊れた記法は、元の文字列を保持し、変換警告を記録する。本文の一部を黙って消すより、表示差を明示して残す方がアーカイブ用途に合う。

安全なHTMLでは、入力中のタグ文字をエスケープし、リンク先は許可したスキームに限定する。外部画像のURLをそのまま埋め込んだHTMLは、オフラインでの完全な保存にはならない。保存した画像への相対参照とし、取得できなかった画像は参照元と状態を表示する。

### 7.4 挿絵の2系統

| 系統 | 元になる情報 | 独自実装で必要な扱い |
|---|---|---|
| 小説へアップロードした画像 | uploadedimage記法、textEmbeddedImages | 対応する画像IDとURLを結び付ける |
| 他のpixiv作品を参照した画像 | pixivimage記法、insert_illustsの結果 | 指定ページ、利用可否、返却されたURLを確認する |

参照画像を通常の画像作品として取り直せることと、小説内で承認された挿絵であることは別である。小説用の取得結果が利用不可・空の場合に、別経路から黙って埋め戻す動作は採用しない。

## 8. 推奨アーキテクチャ

### 8.1 構成

~~~mermaid
flowchart TD
    UI["CLI・拡張・デスクトップ"] --> Input["入力解析と取得計画"]
    Input --> Queue["作品ごとのジョブ"]
    Queue --> Adapter["pixiv取得アダプター"]
    Adapter --> Validate["形式と完全性の検査"]
    Validate --> Store["ローカル保存"]
    Store --> Export["HTML・ZIP等の出力"]
    Queue --> DB["状態台帳"]
    Validate --> DB
    Store --> DB
    DB --> Queue
~~~

取得アダプターはネットワークと認証を担当する。保存エンジンは作品・素材・版・状態を担当する。レンダラーは小説記法や動画派生物を担当する。UIはこれらを呼び出し、状態を表示する。境界を分けることで、pixivの応答変更が全体へ広がるのを抑えられる。

### 8.2 ローカルエンジンから始める理由

ローカルエンジンは、書き込み先・空き容量・再開状態を管理しやすく、集中型サービスの利用者認証・課金・配布URL・一時保存費用が不要である。特に大きい画像やうごイラを扱う際、全データをブラウザのメモリに積んでZIP化する構成を避けやすい。

最初はCLIを用意し、実サイトへのアクセス部分とは別に、合成レスポンスからアーカイブを作る経路を用意する。これにより、作品本文や認証情報をテスト用リポジトリへ含めずに、ページ欠落・ファイル破損・再開・変換を検証できる。

### 8.3 ブラウザ拡張を次に追加する理由

拡張は、現在表示している作品・作者・シリーズの選択と、ユーザーの通常の閲覧セッションとの接続を担う。権限はpixiv関連の必要なホストと操作に絞る。

ローカルエンジンと接続する場合は、任意のWebページから操作できる無認証HTTPサーバーを開かない。候補はNative Messaging、またはlocalhost限定・セッション認証付きの通信である。受信するURL・ファイルパス・作品IDを再検証し、ブラウザ側からの値を信頼し切らない。

拡張からの操作も、保存前の対象一覧・容量目安・保存先を確認できるようにする。大量のジョブを生成した場合でも中断でき、再開時に同じ画像を毎回取り直さないことを重視する。

### 8.4 デスクトップUIは必要に応じて追加する

CLIとデータモデルが安定してから、進捗、作品一覧、エラー理由、保存済み版、シリーズ閲覧をGUIへ載せる。TauriやElectronなどの選択は、配布対象、変換処理、ファイルアクセス、既存コードとの接続を確認してから決める。本資料は特定フレームワークを必須にしない。

スマホだけで処理を完結させる要件は別に評価する。ローカルPCで動くエンジンと、モバイルブラウザだけのアプリでは、ファイル保存・バックグラウンド動作・認証・大容量処理の条件が違う。

## 9. 再開・差分・完全性の設計

### 9.1 ジョブと作品の状態

作品には、queued、fetching、partial、complete、skipped、failedのような状態を持たせる。状態の意味はUIとCLIで共通にする。

| 状態 | 意味 |
|---|---|
| queued | 取得対象として列挙された |
| fetching | 必要データを取得中 |
| partial | 一部は保存できたが必須素材が不足する |
| complete | 必須素材とメタデータの検査を満たす |
| skipped | 指定の条件で意図的に対象外にした |
| failed | 試行したが保存条件を満たせなかった |

ジョブ全体の結果には、列挙完了の有無、候補数、形式別件数、complete数、partial数、skipped数、failed数を含める。「停止せず最後まで処理した」は「全作品を保存できた」と同じではない。

### 9.2 作品単位の確定

1. メタデータから必要な素材一覧を作る。
2. 一時ディレクトリへ素材を保存する。
3. 各素材のサイズ・形式・ハッシュを確認する。
4. 作品manifestを作る。
5. 確定ディレクトリへ移し、最後に台帳をcompleteへ更新する。

途中停止やディスク不足が起きても、未完成ディレクトリを完成品として再利用しない。台帳だけcompleteになってファイルがない場合は、整合性検査で破損と判定する。

### 9.3 版を保持する

作品IDが同じでも本文や画像が更新される。単純なID単位の「取得済み」だけでは更新を検出できない。

候補になる版識別子は、サーバーの更新情報と、取得した内容のハッシュである。カウント類や閲覧者依存フィールドの変化まで内容改訂と扱うと版が増えすぎるため、本文・画像・主要メタデータを分ける。

例として、作者名・作品IDを親ディレクトリ、取得内容のハッシュを版ディレクトリにし、最新の版を台帳が参照する。本文を再取得したときに旧版を黙って上書きしない。削除や閲覧不能の観測は別の履歴とし、それだけでローカル保存済み作品を削除しない。

### 9.4 推奨する台帳

SQLiteなどのローカルDBには、以下を分けて保存する。

| テーブル相当 | 主な内容 |
|---|---|
| works | 種別＋作品ID、作者ID、元ページ、最新観測状態 |
| revisions | 作品ID、版識別子、本文・主要メタデータのハッシュ |
| assets | 版、役割、ページ番号、パス、MIME、サイズ、ハッシュ、状態 |
| series_members | シリーズID、作品ID、順序、観測時刻 |
| jobs | 入力条件、列挙状態、開始・終了、集計 |
| attempts | 作品・素材、結果、HTTP分類、次の再試行予定 |
| permissions | 利用目的ごとの許可状態、根拠URL、確認日 |

これは完成版の設計案である。同梱alphaにこの全てが実装済みという意味ではない。

## 11. 通信・障害時の設計

### 11.1 エラーを分類する

| 状況 | 推奨する扱い |
|---|---|
| 401・認証要求 | 自動再試行を繰り返さず、認証状態を確認できる結果にする |
| 403 | 閲覧権限・サービス側制限等として停止し、成功扱いにしない |
| 404 | 現時点で取得不可として記録する。削除理由を断定しない |
| 429 | Retry-Afterがあれば尊重し、ジョブ全体の発行速度を落とす |
| 5xx・一時的通信断 | 上限付き再試行。連続失敗時は一旦停止する |
| HTMLが返る | JSONや画像として保存する前に拒否する |
| 予期しないJSON構造 | スキーマ変更として記録し、本文空文字に置き換えない |
| 容量不足 | 新規取得を止め、確定済み作品と未完成作品を区別する |

固定の秒数や並列数を「pixivが許容する安全値」と断定する根拠はない。初期設定は少数並列と待機を用い、応答に合わせて減速する。リトライ回数・待機時間・同一ホストの並列数を別々に管理し、失敗した素材だけを再試行する。

### 11.2 URLとファイル名

元ページ入力は許可したpixivホストと既知パスへ限定する。素材URLは取得元レスポンスの構造を確認し、許可する配信ホスト・HTTPSを検証する。リダイレクト後も同じ基準を適用する。

タイトルをファイル名へ使う場合、パス区切り、制御文字、Windows予約名、末尾の空白・ピリオド、極端な長さを処理する。保存先の外へ出るパスは拒否する。衝突回避はタイトルだけでなく、作品種別とIDを使う。

作品の種類ごとに同じ数字IDが存在し得るため、内部キーは「platform、kind、id」を組み合わせる。ページファイルは番号をゼロ埋めし、閲覧ソフトの自然順ソートに依存しない。

## 12. OSS公開までの受入条件

### 12.1 オフラインで確認する条件

| 検証 | 合格条件 |
|---|---|
| 全形式の正規化 | イラスト・複数ページ・うごイラ・小説が共通台帳へ入る |
| 小説記法 | 対応記法が反映され、未知記法の文字が消えない |
| HTML | 本文やタイトル中のタグが実行されない |
| 不正リンク | 危険なURLスキームがクリック可能なリンクにならない |
| 挿絵 | 取得不能が明示され、未承認結果を別経路で埋めない |
| 途中失敗 | 完成した作品を壊さず、再開時に未完だけを処理する |
| 破損検知 | 既存ファイルの改変・欠落を検出できる |
| パス | 悪意あるタイトルやZIP内パスが保存先を逸脱しない |
| 版管理 | 同一IDの本文更新が旧版を破壊しない |
| ページング | 重複・空ページ・カーソル循環で無限ループしない |

テスト入力は自作本文・合成JSON・自作画像を使う。既存作品、Cookie、個人のブックマーク一覧などを、公開テストデータとして同梱しない。

### 12.2 実サイトで別途確認する条件

実サイト検証は、保存を認められた小さい対象を用いて、次の記録を残す。

1. 対象の種類、公開範囲、認証の有無、検証日。
2. APIが返したページ数・素材数と保存結果の一致。
3. 元ページの本文・ルビ・改ページとオフラインHTMLの比較。
4. 小説シリーズの順序、途中ページング、挿絵利用可否。
5. 中断後の再実行で重複取得しないこと。
6. 取得できない対象を「成功」「本文0文字」に誤分類しないこと。

この確認を完了するまでは「全形式の実サイト動作を確認済み」と表示しない。オフラインテストの合格は、ネットワーク経路や認証の動作確認に置き換わらない。

### 12.3 公開物に必要な説明

READMEには、実装済み機能、未実装機能、実サイトで未確認の機能、必要環境、実行例、保存先、エラー時の扱いを書く。APIの非公式性や利用条件の確認を、抽象的な免責文だけで済ませず、各機能の前提として記述する。

ソフトウェアのライセンスと、取得される作品の権利は別である。OSS公開はプログラムの公開を意味し、取得作品の一括再配布や学習利用への許可を自動的に与えない。各利用目的の根拠をメタデータとして管理する。

pixiv公式利用規約ページの本文は本調査環境では取得できていないため、現行条文を確認済みとする断定は行っていない。本資料は技術調査と設計提案であり、公開・運用前の利用条件整理は別途必要である。

公式ヘルプは「全体」「ログインユーザー」「マイピク」「非公開」という公開範囲と、設定による一覧表示の差を説明している。[S9][S10] このため、匿名で得た作品一覧が作者の全投稿を含むとは限らない。公式技術記事もAPIのレート制限と、認証のないデータ収集への制約を説明している。[S11] 間隔を一定にすれば取得を保証される、という仕様ではない。

将来、保存したテキストをAI学習へ使用する場合も、単に「公開作品」「日本国内」「OSSツールで取得」のいずれかだけで結論を出さない。文化庁の説明では、情報解析に関する著作権法30条の4の適用可能性と、享受目的が併存する場合等の例外が区別されている。[S12] 本実装は個別作品の許可・例外適用を判定せず、利用目的ごとの根拠を記録できるよう未確認状態を保持する。

## 13. 実装の優先順位

| 順位 | 範囲 | 到達点 |
|---|---|---|
| 1 | 合成データから全形式のアーカイブ生成 | 保存・変換・失敗分類を検証できる |
| 2 | 単体作品の取得アダプター | 小さな許可対象で実サイト互換性を確認する |
| 3 | 作者列挙と再開 | ページ欠落・途中停止・重複を扱う |
| 4 | シリーズと挿絵 | 読む順序と小説の完全性を向上する |
| 5 | 版管理・検証コマンド | 取得後も破損・更新を確認できる |
| 6 | ブラウザ拡張 | URLの選択と本人の閲覧セッションから操作できる |
| 7 | GUI・変換形式追加 | 既存エンジンを変更せず利用者層を広げる |

GIF・MP4・EPUBなどの追加形式は有用だが、完全性の台帳と元データ保持より先に増やすと、変換成功に見えて取得欠落を見逃す構造になりやすい。最初の公開では、対応形式の数だけでなく「失敗と部分完了が分かること」を品質の基準にする。
