# 保存速度の仕組み

0.2.0-alpha.2時点のコードから確認できる事実と、利用者環境での実測が必要な点を区別する。

## コードから分かること

`rust/transport.rs` の送信処理は、全ワーカーのAPI・画像・ZIPに共有の開始間隔を適用する。TUIの既定は2秒で、要求予算は500回。2秒は本ツールが採用した値で、Pixivが公表する上限値として扱っていない。

| 新規保存の例 | 通常必要な要求 | 開始間隔だけによる最短時間 |
|---|---|---|
| 単体の1枚絵 | 詳細＋ページ情報＋画像＝3回 | 約4秒 |
| 1枚絵16作品の単体URL | 3回×16＝48回 | 約94秒 |
| 20ページの漫画1作品 | 詳細＋ページ情報＋画像20枚＝22回 | 約42秒 |
| うごイラ1作品 | 詳細＋フレーム情報＋ZIP＝3回 | 約4秒＋CRC検査等 |

最初の要求は待たず、N回の開始には `(N−1)×2秒` の間隔が必要、という条件での概算。転送完了時間・書き込み・検査を含む実測値ではない。作者一覧、シリーズのページ送り、小説の表紙・挿絵は追加要求になる。保存済みの健全な作品は媒体を再取得しない。

`--jobs 4` は同時に処理する作品数を増やす。媒体の転送は重ねられるが、共有の送信開始間隔を4倍にはしない。また、拒否応答を共有して後続要求を止めるため、応答ヘッダーの取得までは送信の許可を直列に扱う。大きなファイルは転送の重なりが効く場合があるが、小さな画像を多数取得する場合は開始間隔の影響が大きい。Rust化によるCPU処理の改善だけではこの待機は縮まらない。

保存には媒体転送に加えて、ファイルの同期・原子的な確定、SHA-256の計算と書き込み後の再照合がある。うごイラはZIPメンバーを読み切るCRC検査も行う。保存済み作品の判定でもファイルを読み、ハッシュを確認する。

## 実行結果で確認する

TUIの終了ログ、F3の結果画面、保存先の `last-run.json` に次を追加した。

| JSONの項目 | 計測範囲 |
|---|---|
| `elapsed_seconds` | 保存処理の開始から一覧出力までの経過時間。実行記録自体の書き込みは含まない |
| `rate_wait_seconds` | 共有の開始間隔を守るため、明示的に待機した実時間の合計 |
| `requests` | 実際に開始した要求数。デモ時は模擬要求数 |
| `request_interval_seconds` | オンライン時の間隔設定。デモは0 |

間隔の待機は他作品の転送と重なる。そのため、`elapsed_seconds − rate_wait_seconds` を純粋な転送時間やディスク処理時間とは扱えない。また、送信の許可を待つMutexの待機時間や、応答ヘッダーを待つ時間は `rate_wait_seconds` に加算しない。

利用者の回線速度、相手側の応答時間、ストレージの読み書き別の影響は未測定である。現時点で利用者環境のボトルネックを一つに断定しない。今回の変更はフォルダーを開く操作と計測の追加で、既定の送信間隔・要求予算・停止条件を維持している。
