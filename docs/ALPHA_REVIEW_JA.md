# α版2点の比較と採用判断

2026年10月30日、Linux／Python 3.12.14で提供された2実装を比較した。Archive Labの保存コアを基盤にし、認証・取得とUIを別層にする方針を選んだ。元のソースとテストを変更せず、このリポジトリへ配置している。

| 成果物 | 元ZIP SHA-256 | 既存テスト |
|---|---|---|
| Pixiv Archive Lab 0.1.0a1 | `7b9ee8afd0557f904b4e1791ae5a0ad002728f7d701a94a50332e0e72bea6777` | 33件合格 |
| PxArchive 0.1.0 | `d72ff9b98bee66cfd611c203ae4bd46d6f67ce3376c36c606cc04a269de2a04f` | 16件合格 |

どちらもMIT表示。来歴の自己申告とLICENSEを確認したが、形式的なクリーンルーム認証は行っていない。別実装のテスト数を一つの製品の49件とは扱わない。PxArchiveのアプリケーションや配布wheelは同梱していない。

## 共通条件での結果

両方へArchive Lab同梱の合成応答・媒体を与え、通信アダプターだけを模擬した。保存・レンダリング・キャッシュ判定は各α版をそのまま使い、GIF変換を無効にした。実際の作品IDではない。

| 条件 | Archive Lab | PxArchive |
|---|---|---|
| 4形式の基本保存 | 4件保存 | 4件保存 |
| 直接アップロード＋表示可能な作品参照挿絵 | 本文のローカル画像2点 | 直接アップロード1点。作品参照はリンク |
| 詳細が3ページ、ページ応答が2ページ | failed | 保存済み扱い |
| 小説の表紙が取得不能 | 本文を保持しpartial | 新規保存1件・失敗なし |
| 保存後の画像削除 | 検出・修復 | 保存済み扱いで戻らない |
| 保存後の画像を同じ長さの別バイト列に変更 | 検出・修復 | 保存済み扱いで戻らない |
| フレーム名は一致するがZIP内部のCRCが不一致 | **completeとしてしまう** | **新規保存としてしまう** |
| 同一IDの小説を改訂後、通常の再実行 | 保存済みとしてスキップ。更新検出・版保持は未実装 | 同左 |

ZIPの試験は、中央ディレクトリを保ったままメンバーを1バイト変更し、標準ライブラリの `zipfile.testzip()` が不一致を検出することを独立の基準にした。通常の再開と、明示的な更新確認は別機能。最後の行は再開のバグではなく、更新確認機能の不足を示す。

## 起動の通し確認

- Archive Lab：別プロセスで `plan → fetch → verify → pack → fetch`。4件保存、4件検査一致、ZIP出力のCRC正常、再実行時の本文・媒体の再取得なし。
- PxArchive：Pixiv通信だけを合成に置き換え、ローカルHTTPサーバーを起動。画面200、トークンなし操作403、ジョブ受理202、finished、ZIP取得200を確認。媒体完全性の証明とは区別した。
- PxArchive同梱wheel：PythonとHTMLの8ファイルが元ソースと一致し、RECORDのハッシュ・サイズも一致。署名やWindows導入の検証ではない。

## 採用理由と残作業

保存品質を優先する今回の要件では、Archive Labのページ照合、欠損状態、原文・参照挿絵、整合性検査が土台に適していた。PxArchiveのUIをそのまま採用すると、保存済み判定と完了表示の改修が多い。

次はZIP内部のCRC・デコード検査、取得部の分離、refreshと不変な旧版、DBとファイルの回復手順を追加する。実サイト・本人セッション・Windows実機の受入は未完了。完成版としては扱わない。
